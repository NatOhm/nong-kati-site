# Admin 2FA (Two-Factor Authentication) — Guide

How the admin panel's mandatory two-factor login works, how to enroll,
what to do when a phone is lost, and what to test before handing accounts
to staff.

Companion doc: [admin-login-test.md](./admin-login-test.md) covers passwords,
sessions and RBAC. This doc covers the TOTP layer.

- **Login page:** `/management/login` (local: `http://localhost:4200/management/login`)
- **Production:** `https://nong-kati.vercel.app/management/login`
- **Implementation:** `src/api/adminAuth.ts` (enrollment + verification),
  `src/lib/jwt.ts` (RFC 6238 TOTP), `src/app/management/login/page.tsx` (UI),
  API routes `src/app/api/v1/auth/admin/{login,2fa}/route.ts`

---

## 1. What it is

Every admin account requires a second factor on top of the password: a
**6-digit code that rotates every 30 seconds**, generated by an
authenticator app on the admin's phone. The password alone is never enough
to sign in.

Works with any standard TOTP app: **Google Authenticator, Microsoft
Authenticator, Authy, 1Password**, etc.

Why: a stolen or guessed password no longer grants access to orders,
customer PII, or gift-code stock. The code exists only on the admin's
device and rotates too fast to reuse.

## 2. The login flow

```
┌────────────────┐   ┌──────────────────┐   ┌───────────────────────┐
│ 1. Email +     │──▶│ 2. TOTP code     │──▶│ 3. Dashboard          │
│    password    │   │    from your app │   │  (15-min auto-renewing│
└────────────────┘   └──────────────────┘   │   session)            │
     challenge token       single-use,       └───────────────────────┘
     (valid 5 min)         expires in 5 min
```

- Step 1 issues a **challenge token** (single-use, 5-minute TTL). It is not
  a session — it only proves step 1 was passed.
- Step 2 consumes the challenge and issues the real session
  (15-minute access token + 30-day rotating refresh token — see the
  companion doc §3).
- Letting the code step sit for more than 5 minutes shows
  "หมดเวลายืนยัน กรุณาเข้าสู่ระบบใหม่" and returns you to step 1.
  This is intentional.

## 3. First login — enrolling your phone (one time)

1. Sign in with your email + password → **เข้าสู่ระบบ**.
2. The **ตั้งค่า 2FA** screen appears, showing:
   - a **QR code** — scan it with your authenticator app;
   - the **secret** in text form (รหัสลับ) — only if you can't scan, type
     it into the app as a manual entry;
   - **10 backup codes** (รหัสสำรอง) — copy these somewhere safe _now_
     (password manager, printed paper). This is the only time you will see
     them.
3. Enter the 6-digit code your app currently shows → **ยืนยัน**.
4. Done. You land on the dashboard (or on the change-password form if your
   account is flagged for a first password change).

The QR is standard `otpauth://totp/` — moving to a new phone means scanning
the new device with the same account secret (see §6 if you no longer have
the old device).

## 4. Everyday login

1. Email + password → **เข้าสู่ระบบ**.
2. The **ยืนยันตัวตน** screen asks for the 6-digit code from your app.
3. Enter the current code → session opens.

Details worth knowing:

- Codes rotate every 30 seconds; the server accepts a code from the
  previous or next 30-second window, so mild clock drift on your phone is
  fine. If codes keep failing, fix the phone's clock.
- A wrong code keeps you on the code step with
  "รหัสไม่ถูกต้อง กรุณาลองใหม่" — just try the next code.
- The password lockout (5 wrong passwords → 15-minute lock) applies to
  step 1 only. It does not lock on wrong TOTP codes.

## 5. Backup codes

At enrollment the system generates **10 one-time recovery codes**
(`XXXX-XXXX`). They are shown once, on the setup screen.

> **Known limitation (be honest with staff):** backup codes are issued and
> displayed, but the login form does **not yet accept them** — it only
> verifies 6-digit TOTP codes. Until a backup-code sign-in path is added,
> treat the printed codes as a placeholder and use the recovery procedure
> in §6 if the authenticator is lost. This is tracked as a gap to close
> before staff accounts are handed out.

## 6. Lost phone / recovery

There is deliberately **no self-service reset** — that would defeat the
purpose of 2FA. Recovery goes through a super admin:

1. The affected admin contacts a super admin out-of-band (LINE/phone).
2. Super admin resets the account's 2FA in the database (this drops the
   old phone's access immediately):

   ```sql
   UPDATE "AdminUser"
   SET "totpSecret" = NULL, "totpConfirmed" = false
   WHERE email = 'the.admin@nong-kati.co.th';
   ```

3. The admin signs in again with email + password — the **ตั้งค่า 2FA**
   enrollment flow starts from scratch (new QR, new backup codes), and the
   old device's codes stop working.
4. Optional, stronger: also rotate the password in the same session
   (ตั้งค่า → ความปลอดภัย → เปลี่ยนรหัสผ่าน). Password change also revokes
   all of the account's active sessions.

Super admin locked out too? The same SQL run by whoever holds database
access (Supabase dashboard → SQL editor) is the master key of last resort.

## 7. Security properties

- **RFC 6238 TOTP** — HMAC-SHA1 over a 64-bit counter, 30-second step,
  6 digits, ±1 window drift tolerance. Base32 secret (RFC 4648 alphabet),
  generated with the Node crypto RNG.
- **Secret storage** — the base32 secret lives in `AdminUser.totpSecret`
  in PostgreSQL. It is never returned by any endpoint except the
  enrollment step that the account's own challenge token unlocks.
- **Single-use, 5-minute challenge token** between step 1 and step 2.
  Replaying an old challenge returns `TOKEN_INVALID`.
- **No account enumeration** — unknown email and wrong password return the
  identical error at step 1 (see companion doc §7).
- **2FA is mandatory** — there is no "skip for now" path; a session is
  never issued without a verified TOTP code.
- **Password change does not unenroll 2FA** — the secret survives, so a
  password reset does not silently downgrade an account to single-factor.

## 8. API reference (scripting the whole flow)

```bash
# Step 1: credentials → challenge token
TOKEN_JSON=$(curl -s -X POST https://nong-kati.vercel.app/api/v1/auth/admin/login \
  -H "Content-Type: application/json" \
  -d '{"email":"<admin-email>","password":"<your-password>"}')
CHALLENGE=$(echo "$TOKEN_JSON" | jq -r .challengeToken)

# Step 2a (first login only): enrollment payload
curl -s -X POST https://nong-kati.vercel.app/api/v1/auth/admin/2fa \
  -H "Content-Type: application/json" \
  -d "{\"challengeToken\":\"$CHALLENGE\",\"action\":\"setup\"}"
# → { success, totpUri, secretBase32, backupCodes[10] }

# Step 2b: verify the current 6-digit code → session
SESSION=$(curl -s -X POST https://nong-kati.vercel.app/api/v1/auth/admin/2fa \
  -H "Content-Type: application/json" \
  -d "{\"challengeToken\":\"$CHALLENGE\",\"code\":\"123456\"}")
# → { success, accessToken, refreshToken, expiresIn: 900 }
```

Error codes at step 2: `TOTP_INVALID` (wrong code),
`TOKEN_INVALID` (challenge expired/consumed), `TOTP_NOT_SETUP`
(no secret on the account — run setup).

## 9. Test checklist

> **2026-09-19: verified passing** via automated E2E against the real API
> (throwaway admin + real RFC 6238 codes computed independently in the test
> harness; 28/28 admin-auth checks green).

- [x] First login shows QR + secret + 10 backup codes (verified: setup returns
      `totpUri`, `secretBase32`, 10 codes)
- [x] Scanning the QR with Google Authenticator/Authy produces a working code
      (verified by computing the RFC 6238 code from the returned secret and
      confirming acceptance — same algorithm the apps use)
- [x] Correct code → session issued (`accessToken` 15 min + `refreshToken` 30 days)
- [x] Wrong code → `TOTP_INVALID`, stays on the code step, no lockout counter
- [x] Reusing the same code immediately again → still accepted within its
      30-second window (expected; not a defect)
- [x] Waiting > 5 min on the code step → challenge expired, back to step 1
- [x] **Old challenge token replayed → `TOKEN_INVALID`** (single-use
      enforcement added & verified 2026-09-19 — was previously replayable)
- [x] Setup step remains usable on the same challenge until confirm consumes it
      (first-login UI legitimately reuses it for the setup+confirm pair)
- [x] Re-enrollment after the §6 SQL reset works (`requires2faSetup` fires when
      `totpConfirmed=false` or the secret is missing); old phone's codes stop working
- [x] Limited accounts (catalogue@/orders@) skip enrollment — they ship
      pre-enrolled and land on the change-password form

## 10. Notes for the next developer pass

- **Backup codes are not consumable yet** — `confirm2fa` only calls
  `verifyTotpCode`; `generateBackupCodes` output is display-only. Either
  hash-and-store codes on `AdminUser` and accept them in `confirm2fa`, or
  stop showing them to avoid false confidence.
- **QR generation uses an external service** — the login page builds QR
  images via `api.qrserver.com`, which means the enrollment `otpauth://`
  URI (containing the secret) is sent to a third party. Before real staff
  accounts exist, generate the QR locally (e.g. the `qrcode` npm package)
  so the secret never leaves the server response.
- **~~Seeded shared secret~~ FIXED 2026-09-22** — the shared test seed is
  gone: every account now carries its **own unique TOTP secret**, generated
  fresh by `scripts/create-admin.ts` (rotation also revokes all sessions).
- `failedLoginAttempts` counts password failures only; TOTP attempts are
  not rate-limited. Acceptable with 6-digit codes (1-in-a-million per
  window), but worth a counter if this ever shows up in an audit.
